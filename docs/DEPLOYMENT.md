## پیش‌نیازها

- **سرور لینوکس** با Docker Engine نسخهٔ ۲۳ یا بالاتر (BuildKit که در این نسخه‌ها پیش‌فرض است؛ Dockerfile از
  `RUN --mount=type=cache` استفاده می‌کند). برای هر فروشگاه دست‌کم ۱ گیگابایت رم در نظر بگیرید؛
  بهینه‌سازی تصاویر حافظه می‌خواهد.
- **دامنه و گواهی TLS** برای فروشگاه (مثلاً با Let's Encrypt) و **nginx نسخهٔ 1.25.1 یا بالاتر** جلوی کانتینر
  (برای دستور `http2 on;`؛ در نسخه‌های قدیمی‌تر به‌جایش `listen 443 ssl http2;` بنویسید). فشرده‌سازی brotli
  ماژول `ngx_brotli` را می‌خواهد (اختیاری).
- **بک‌اند فایرفلای** که روی یک آدرس عمومی HTTPS در دسترس است (مثلاً `https://api.shop.ir`) و دسترسی
  **superuser** به پنل آن، برای ساخت کلید API.
- برای ساخت بدون Docker یا توسعه: **Node.js نسخهٔ 22.12 یا بالاتر** (`sanitize-html` به `require(esm)` نیاز
  دارد؛ نسخهٔ دقیق در `.nvmrc` است) و **pnpm** از طریق `corepack enable` (نسخه در `packageManager` فایل
  `package.json` ثابت شده).

ساختن ایمیج به بک‌اند نیاز ندارد: همهٔ تنظیمات فروشگاه در زمان اجرا خوانده می‌شود.

## متغیرها: آرگومان ساخت در برابر محیط اجرا

فقط یک مقدار در زمان **ساخت** لازم است: `FIREFLY_API_URL` به‌عنوان `--build-arg`. دلیلش این است که Next.js
فهرست میزبان‌های مجاز `next/image` (برای بهینه‌سازی تصاویر) را هنگام ساخت در خروجی می‌نویسد. همین مقدار را
در زمان اجرا هم بدهید. بقیهٔ متغیرها فقط **زمان اجرا** هستند و با `--env-file` به کانتینر داده می‌شوند؛ با
تغییر آن‌ها کافی است کانتینر را از نو اجرا کنید، ساخت دوباره لازم نیست.

> اگر چند فروشگاه به یک API مشترک وصل‌اند، یک ایمیج برای همه کافی است. اگر هر فروشگاه API خودش را دارد
> (حالت معمول)، برای هر فروشگاه یک ایمیج با `FIREFLY_API_URL` خودش بسازید.

فایل نمونه با توضیح هر متغیر: [`.env.example`](../.env.example). مقدارهای خالی یا فقط فاصله «تنظیم‌نشده»
حساب می‌شوند و یک جفت کوتیشن دور مقدار برداشته می‌شود. رنگ‌ها را در فایل `.env` حتماً در کوتیشن بنویسید
(`"#4F46E5"`)، چون `#` بدون کوتیشن شروع توضیح است. اگر متغیری نامعتبر باشد، برنامه در لاگ فهرست همهٔ
متغیرهای نامعتبر را (فقط نام و قاعده، هرگز مقدار) چاپ می‌کند، صفحه‌ها خطای ۵۰۰ می‌دهند و بررسی سلامت
(`/healthz/`) پاسخ ۵۰۳ می‌دهد تا کانتینر unhealthy شود.

| متغیر | الزامی در تولید؟ | کِی | نمونه | توضیح |
| --- | --- | --- | --- | --- |
| `FIREFLY_API_URL` | بله | ساخت + اجرا | `https://api.shop.ir` | آدرس **عمومی** API فایرفلای (اسلش پایانی حذف می‌شود؛ بدون `?` و `#`، وگرنه برنامه اجرا نمی‌شود). پایین‌تر توضیح داده شده چرا نباید آدرس داخلی باشد. |

| `FIREBASE_PROJECT_ID` | خیر | اجرا | `shop-12345` | شناسهٔ پروژهٔ Firebase. |

| `FIREBASE_APP_ID` | خیر | اجرا | `1:123…:web:abc…` | شناسهٔ اپلیکیشن وب. |
| `FIREBASE_VAPID_KEY` | خیر | اجرا | `BKx…` | کلید VAPID. |
| `FEATURE_COMPARE` | خیر | اجرا | `false` | مقایسهٔ محصولات (`true`، `false`، `1`، `0`؛ پیش‌فرض روشن). |

| `FEATURE_PWA` | خیر | اجرا | `true` | نصب‌پذیری PWA و سرویس‌ورکر. |

این‌ها را خود ایمیج تنظیم کرده و معمولاً دست نمی‌خورند:

| متغیر | مقدار در ایمیج | توضیح |
| --- | --- | --- |
| `NODE_ENV` | `production` | حالت تولید؛ در این حالت مقدارهای پیش‌فرض توسعه (localhost) هرگز اعمال نمی‌شوند و سه متغیر اول الزامی‌اند. |
| `PORT` | `3000` | پورت داخل کانتینر. |
| `HOSTNAME` | `0.0.0.0` | آدرسی که سرور روی آن گوش می‌دهد. |
| `NEXT_TELEMETRY_DISABLED` | `1` | خاموش‌بودن تله‌متری Next.js. |
| `KEEP_ALIVE_TIMEOUT` | `65000` | مدت باز ماندن اتصال keep-alive بی‌کار، به میلی‌ثانیه. باید **بیشتر** از `keepalive_timeout` در upstream مربوط به nginx (۶۰ ثانیه در نمونه) باشد؛ وگرنه nginx ممکن است اتصالی را که Node همان لحظه بسته دوباره به کار ببرد و گاه‌به‌گاه خطای ۵۰۲ بدهد. پیش‌فرض خود Node فقط ۵ ثانیه است. |

`NODE_VERSION` هم آرگومان اختیاری ساخت است (پیش‌فرض در Dockerfile، باید ۲۲.۱۲ یا بالاتر باشد).

### چرا `FIREFLY_API_URL` باید آدرس عمومی API باشد

- بک‌اند آدرس تصاویر را از هدر `Host` همان درخواست می‌سازد و Node هدر `Host` دلخواه را نادیده می‌گیرد. اگر
  فروشگاه API را با آدرس داخلی (مثل `http://web:8000`) صدا بزند، همهٔ آدرس تصاویر `http://web:8000/media/…`
  می‌شوند که برای مرورگر بی‌معناست؛ Django هم میزبان ناشناخته را با خطای ۴۰۰ `DisallowedHost` (HTML) رد
  می‌کند.
- فروشگاه مسیرهای `/media/`، `/static/`، `/sitemap.xml` و بازگشت بانک را به همین آدرس می‌فرستد و Next.js
  آدرس مقصد را در یک هدر داخلی پاسخ (`x-middleware-rewrite`) نشان می‌دهد؛ پس این آدرس به‌هرحال دیده
  می‌شود و نباید چیز محرمانه‌ای در آن باشد.
- فهرست میزبان مجاز تصاویر از همین مقدار ساخته می‌شود.

## ساخت و اجرای ایمیج

از ریشهٔ مخزن:

```bash
docker build \
  --build-arg FIREFLY_API_URL=https://api.shop.ir \
  -t firefly-front:shop-2026-10-16 .
```

برای هر فروشگاه یک فایل env بسازید (مثلاً `/etc/firefly/shop.env` با دسترسی `600`) از روی `.env.example`:

```dotenv
FIREFLY_API_URL=https://api.shop.ir
FIREFLY_API_KEY=<کلید پنل>
SITE_URL=https://shop.ir
STORE_PRESET=digital
CLIENT_IP_HEADER=x-real-ip
```

و کانتینر را فقط روی localhost منتشر کنید (پورت ۳۰۰۰ هرگز نباید از اینترنت در دسترس باشد، چون برنامه به
`X-Real-IP` اعتماد می‌کند):

```bash
docker run -d --name shop-front --restart unless-stopped \
  --env-file /etc/firefly/shop.env \
  -p 127.0.0.1:3000:3000 \
  firefly-front:shop-2026-10-16
```

فروشگاه دوم روی همان سرور: فایل env و نام کانتینر دیگر و پورت دیگر (`-p 127.0.0.1:3001:3000`) و یک بلوک
`server` دیگر در nginx.

فونت اختصاصی بدون ساخت دوباره: فایل را هنگام اجرا mount کنید و `THEME_FONT=custom` بگذارید
(`-v /etc/firefly/shop-font.woff2:/app/public/fonts/custom/font.woff2:ro`). فایل باید پیش از شروع کانتینر
وجود داشته باشد.

نمونهٔ معادل با Docker Compose:

```yaml
services:
  shop-front:
    image: firefly-front:shop-2026-10-16
    restart: unless-stopped
    env_file: /etc/firefly/shop.env
    ports:
      - '127.0.0.1:3000:3000'
```

بدون Docker (مثلاً با systemd): روی Node ۲۲.۱۲ به بالا، `pnpm install --frozen-lockfile` و سپس
`FIREFLY_API_URL=https://api.shop.ir pnpm build` و با متغیرهای محیطی بالا `pnpm start:standalone`. این
اسکریپت دقیقاً همان کاری را می‌کند که ایمیج: `.next/static` و `public` را کنار `server.js` خروجی standalone
کپی می‌کند و آن را اجرا می‌کند (`KEEP_ALIVE_TIMEOUT` را هم اگر تنظیم نشده باشد ۶۵۰۰۰ می‌گذارد).

### رشد کش داده روی دیسک (`.next/cache/fetch-cache`)

فروشگاه پاسخ‌های عمومی API (صفحهٔ کالا، دسته‌ها، فهرست‌ها و فیلترهایشان) را در کش داده Next.js نگه
می‌دارد و هر پاسخ یک فایل در `/app/.next/cache/fetch-cache` داخل کانتینر است. هر ترکیب تازه از فیلترها،
مرتب‌سازی و شمارهٔ صفحهٔ یک فهرست (مثلاً `?brand=…&min_price=…&page=7` که یک بازدیدکننده یا خزنده ساخته)
یک فایل تازه می‌سازد و **Next.js این فایل‌ها را هرگز پاک نمی‌کند**؛ پس این پوشه با گذشت زمان، مخصوصاً
زیر خزنده‌ها، تا چند گیگابایت بزرگ می‌شود. هیچ مدخلی بیش از ۵ دقیقه معتبر نیست و بعد از آن دوباره از API
خوانده می‌شود، پس پاک‌کردن فایل‌های کهنه بی‌خطر است: هزینه‌اش فقط یک درخواست تازه به API است. یکی از این
دو راه (یا هر دو) را به کار ببرید:

- **tmpfs:** پوشهٔ کش را روی حافظه بگذارید. سقف اندازه دارد و با هر بار اجرای دوبارهٔ کانتینر خالی
  می‌شود. `uid=1000` همان کاربر `node` ایمیج است؛ این مقدار از رم کانتینر برداشته می‌شود (کش تصاویر
  بهینه‌شده، `images/`، هم در همین پوشه است). وقتی پر شود، برنامه فقط هشدار
  `Failed to update prerender cache` در لاگ می‌نویسد و مدخل تازه را کش نمی‌کند؛ از کار نمی‌افتد.

  ```bash
  docker run -d --name shop-front --restart unless-stopped \
    --env-file /etc/firefly/shop.env \
    -p 127.0.0.1:3000:3000 \
    --tmpfs /app/.next/cache:rw,size=512m,uid=1000,gid=1000,mode=0755 \
    firefly-front:shop-2026-10-16
  ```

  در Compose: زیر سرویس `tmpfs: ['/app/.next/cache:rw,size=512m,uid=1000,gid=1000,mode=0755']`.

- **پاک‌سازی دوره‌ای:** مدخل‌هایی را که یک ساعت است دست نخورده‌اند پاک کنید (مدخل‌های پربازدید هر
  چند دقیقه بازنویسی می‌شوند و می‌مانند). نمونهٔ cron روی میزبان، هر ساعت:

  ```cron
  17 * * * * docker exec shop-front find /app/.next/cache/fetch-cache -type f -mmin +60 -exec rm -f {} +
  ```

  بدون Docker همان دستور `find` را روی `.next/standalone/.next/cache/fetch-cache` در پوشهٔ برنامه اجرا
  کنید.

## nginx جلوی فروشگاه

فایل نمونه: [`deploy/nginx.conf.example`](../deploy/nginx.conf.example). شامل TLS، انتقال `www` به دامنهٔ
اصلی، gzip و brotli، کش یک‌ساله و immutable برای `/_next/static/`، `client_max_body_size 6m` (آپلود رسید
کارت‌به‌کارت و تصویر پروفایل تا ۵ مگابایت) و خاموش‌بودن بافر پاسخ‌ها (صفحه‌ها به‌صورت جریانی ارسال می‌شوند).

- **فشرده‌سازی یک بار، در nginx.** nginx با `proxy_set_header Accept-Encoding "";` هدر `Accept-Encoding`
  را از درخواست به برنامه حذف می‌کند؛ پس برنامه بدنهٔ فشرده‌نشده می‌فرستد و nginx هر پاسخ را یک بار با
  brotli یا gzip فشرده می‌کند (`text/x-component`، یعنی دادهٔ RSC هر جابه‌جایی بین صفحه‌ها، در
  `gzip_types` و `brotli_types` هست). خود Next.js فقط وقتی gzip می‌کند که پروکسی‌ای این هدر را حذف نکرده
  باشد (`compress: true`)؛ پس بدون nginx هم پاسخ‌ها gzip می‌شوند. اگر `location` تازه‌ای با
  `proxy_set_header` خودش اضافه کنید، این هدرها را آنجا تکرار کنید: nginx هدرهای سطح `server` را به چنین
  `location`ی به ارث نمی‌دهد.
- **هدرهای امنیتی را خود برنامه می‌فرستد** (`src/config/security-headers.ts`، روی همهٔ پاسخ‌ها):
  `X-Frame-Options: SAMEORIGIN` و `Content-Security-Policy: frame-ancestors 'self'` (هیچ سایت دیگری
  نمی‌تواند فروشگاه را در iframe نشان دهد؛ جلوی clickjacking)، `X-Content-Type-Options: nosniff` و
  `Referrer-Policy: strict-origin-when-cross-origin`. nginx فقط `Strict-Transport-Security` را اضافه
  می‌کند؛ این چهار هدر را در nginx تکرار نکنید (دو بار فرستاده می‌شوند). اگر می‌خواهید فروشگاه داخل iframe
  دامنهٔ دیگری نمایش داده شود، **هر دو** هدر قاب را در همان فایل عوض کنید (مثلاً
  `frame-ancestors 'self' https://partner.example` و حذف `X-Frame-Options`) و ایمیج را دوباره بسازید.
- **HTML صفحه‌ها را در CDN یا `proxy_cache` کش نکنید**، مگر کلید کش کوکی `ff_auth` را هم در بر بگیرد:
  سربرگ وضعیت ورود کاربر را از همان HTML اول نشان می‌دهد (برنامه `Cache-Control: private, no-store`
  می‌فرستد). فقط `/_next/static/` برای همه یکسان و قابل کش است.
- **لاگ دسترسی بدون کلید پرداخت.** نشانی برخی صفحه‌ها و درخواست‌ها کلید پرداخت سفارش را در خود دارد:
  توکن لینک پرداخت (`/order/pay/<token>/`، `/api/bff/order/pay/<token>/…`، `/api/bff/payment/link/<token>/…`
  و صفحهٔ ورودی که به آن برمی‌گردد، `/login/?next=/order/pay/<token>/`)، شناسهٔ پرداخت (`/payment/callback/?payment=…`،
  `/payment/card-transfer/<uuid>/`، `/api/bff/payment/<uuid>/…`) و توکن بازگشت بانک
  (`/api/v1/payment/gateway/callback/<درگاه>/<token>/`). هر کسی یکی از این نشانی‌ها را بخواند می‌تواند سفارش
  مهمان را بپردازد یا لغو کند. لاگ پیش‌فرض nginx خط درخواست را همان‌طور که رسیده می‌نویسد؛ پس فایل نمونه با
  سه `map` روی `$request_uri` این بخش‌ها را با `<token>` و `<uuid>` (تا دو شناسه در یک نشانی) جایگزین
  می‌کند و هر سه `server` فروشگاه با `log_format firefly_masked` همین نشانیِ پوشانده را می‌نویسند (بدون
  Referer). فهرست کامل الگوها در خود فایل است؛ با nginx 1.27.5 روی همهٔ این شکل‌ها آزموده شده و هیچ‌کدام
  به لاگ دسترسی نرسید.
  - `map`ها و `log_format` در سطح `http` و **یک بار برای هر سرور** تعریف می‌شوند؛ فروشگاه دوم روی همان
    سرور همان‌ها را به کار می‌برد (nginx دومین `log_format` هم‌نام را نمی‌پذیرد).
  - هر `access_log` تازه‌ای که اضافه می‌کنید (در `server` یا `location`) باید `firefly_masked` را نام ببرد؛
    وگرنه قالب پیش‌فرض نشانی کامل را می‌نویسد.
  - **لاگ خطای nginx را نمی‌شود پوشاند:** درخواستی که به برنامه نرسد (۵۰۲، پایان مهلت) با خط کامل درخواست
    در `error_log` نوشته می‌شود. دسترسی و مدت نگه‌داری این لاگ را به اندازهٔ خود این کلیدها محدود کنید. اگر
    نمی‌خواهید آن خطوط نوشته شوند، `location` جدای بخش [لاگ خطا بدون کلید پرداخت](#لاگ-خطا-بدون-کلید-پرداخت-اختیاری)
    را بگذارید.
  - **هر پروکسی، load balancer یا CDN دیگری** جلوی فروشگاه (یا در حالت تک‌دامنه بین فروشگاه و API) هم باید
    همین مسیرها را بپوشاند یا لاگ نکند. در حالت تک‌دامنه درخواست‌های خود فروشگاه به `/api/v1/order/pay/…`،
    `/api/v1/payment/link/…` و `/api/v1/payment/<uuid>/…` از همین nginx می‌گذرند و همین `map`ها آن‌ها را هم
    می‌پوشانند. لاگ درخواست خود بک‌اند جداست.
  - خود برنامهٔ فروشگاه در تولید هیچ لاگ درخواستی نمی‌نویسد و BFF مسیرها را لاگ نمی‌کند.
- **keep-alive:** `keepalive_timeout 60s` در بلوک `upstream` باید کمتر از `KEEP_ALIVE_TIMEOUT` برنامه
  (۶۵ ثانیه) بماند تا همیشه nginx اتصال بی‌کار را زودتر ببندد.
- **چند فروشگاه روی یک سرور:** هر فروشگاه یک `upstream` با نام و پورت جدا می‌خواهد (مثلاً
  `firefly_shop2` روی `127.0.0.1:3001`) و `server` خودش.

همهٔ مسیرها به کانتینر می‌روند؛ خود فروشگاه `/media/`، `/static/`، `/sitemap.xml` و مسیر بازگشت بانک
`/api/v1/payment/gateway/callback/…` را با همان متد و بدنه و اسلش پایانی به API می‌فرستد. پس در حالت
دامنه‌های جدا، nginx فروشگاه قاعدهٔ خاصی برای این مسیرها لازم ندارد.

### لاگ خطا بدون کلید پرداخت (اختیاری)

خطای upstream (۵۰۲، پایان مهلت) با سطح `error` و خط کامل درخواست در `error_log` ثبت می‌شود. یک
`location` جدا برای مسیرهایی که کلید پرداخت را در نشانی دارند، با `error_log … crit`، این خطاها را اصلاً
ثبت نمی‌کند (فقط خطاهای بحرانی خود nginx می‌مانند). در حالت دامنه‌های جدا، داخل `server` فروشگاه و پیش از
`location /`:

```nginx
# صفحه‌ها و درخواست‌های BFF با کلید پرداخت، صفحه‌های ورود که `next` آن‌ها کلید را دارد
# (/login/?next=/order/pay/<token>/) و بازگشت بانک، که خود فروشگاه به API می‌فرستد.
location ~* ^/(order/pay|payment|login|register|forgot-password|api/bff/order/pay|api/bff/payment|api/v1/payment/gateway/callback)/ {
    error_log /var/log/nginx/<shop>.error.log crit;
    proxy_pass http://firefly_storefront;
    # صفحه‌های /order/pay/ و /payment/ جریانی ارسال می‌شوند، مثل `location /`.
    proxy_buffering off;
}
```

- `proxy_pass` به ارث نمی‌رسد و `proxy_buffering off` در فایل نمونه فقط در `location /` است (یک
  `location` از `location` دیگر چیزی به ارث نمی‌برد)؛ پس هر دو باید همین‌جا باشند (بدون
  `proxy_buffering off` اولین بایت صفحه تا پر شدن بافر یا پایان پاسخ برنامه منتظر می‌ماند). اگر
  `location /` شما دستور دیگری هم دارد، **همهٔ** دستورهای آن را اینجا تکرار کنید.
- `proxy_set_header`های سطح `server` (`Host`، `X-Real-IP`، `X-Forwarded-*` و `Accept-Encoding ""`) فقط
  وقتی به این `location` می‌رسند که خودش **هیچ** `proxy_set_header`ی نداشته باشد؛ با اولین
  `proxy_set_header` در آن، همه را اینجا تکرار کنید (وگرنه مثلاً `X-Real-IP` نمی‌رسد و همهٔ مهمان‌ها با IP
  خود nginx شمرده می‌شوند). `add_header` (HSTS) هم همین قاعده را دارد. `access_log` سطح `server`
  (`firefly_masked`) هم به ارث می‌رسد، مگر این `location` `access_log` خودش را داشته باشد.
- `~*` به بزرگی و کوچکی حروف حساس نیست (مثل `map`های لاگ دسترسی) و چون regex است، بر `location /` (و در
  حالت تک‌دامنه بر `location /api/v1/`) مقدم است.
- خطاهای upstream مسیرهای دیگر همین پیشوندها (مثلاً `/api/bff/payment/methods/` یا ورود بدون `next`) هم
  ثبت نمی‌شوند؛ دسترس‌بودن را با `/healthz/` و لاگ دسترسی پایش کنید.

در حالت تک‌دامنه، `location /` و `location /api/v1/` هر کدام `proxy_set_header` خودشان را دارند (پس از
سطح `server` چیزی نمی‌گیرند) و مسیرهای کلیددار `/api/v1/` (درخواست‌های خود فروشگاه به `/api/v1/order/pay/…`،
`/api/v1/payment/link/…` و `/api/v1/payment/<uuid>/…`، و بازگشت بانک) باید به Django بروند، نه به فروشگاه، وگرنه
حلقه درست می‌شود. پس دو بلوک لازم است و هر کدام **همهٔ** دستورهای `location` اصلی خود را تکرار می‌کند:

```nginx
location ~* ^/(order/pay|payment|login|register|forgot-password|api/bff/order/pay|api/bff/payment)/ {
    error_log /var/log/nginx/shop.error.log crit;
    proxy_pass http://127.0.0.1:3000;            # همهٔ دستورهای `location /`
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header Accept-Encoding "";
    proxy_buffering off;
}
location ~* ^/api/v1/(order/pay|payment)/ {
    error_log /var/log/nginx/shop.error.log crit;
    proxy_pass http://127.0.0.1:8000;            # همهٔ دستورهای `location /api/v1/`
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
}
```

هر دو شکل با nginx 1.27 آزموده شده‌اند (`nginx -t` و درخواست‌های واقعی): هدرها و پاسخ جریانی همان
`location /` را دارند و ۵۰۲ این مسیرها هیچ خطی در `error_log` نمی‌نویسد.

### IP بازدیدکننده: `X-Real-IP` و `CLIENT_IP_HEADER`

بک‌اند برای مهمان‌ها محدودیت تعداد درخواست را **به‌ازای هر IP** حساب می‌کند. همهٔ درخواست‌های فروشگاه از
یک IP (سرور فروشگاه) می‌آیند، پس فروشگاه IP واقعی بازدیدکننده را در `X-Forwarded-For` به API می‌فرستد (فقط
روی درخواست‌های بدون کش: BFF، ریدایرکت، لینک کوتاه، تمدید نشست و بازگشت بانک). این IP را از هدری می‌خواند
که نامش در `CLIENT_IP_HEADER` است.

- nginx باید این هدر را **بازنویسی** کند، نه اضافه: `proxy_set_header X-Real-IP $remote_addr;`. مرورگر
  نمی‌تواند مقداری را که nginx بازنویسی می‌کند جعل کند.
- `CLIENT_IP_HEADER` را **هرگز** `x-forwarded-for` نگذارید، مگر لبهٔ شما این هدر را کاملاً بازنویسی کند.
  `$proxy_add_x_forwarded_for` به مقداری که مرورگر فرستاده اضافه می‌کند و هر کسی می‌تواند با فرستادن
  `X-Forwarded-For: 1.2.3.4` خودش را جای دیگری جا بزند. فروشگاه اولین مقدار فهرست را برمی‌دارد.
- پشت Cloudflare یا CDN مشابه: یا `CLIENT_IP_HEADER=cf-connecting-ip` (فقط وقتی سرور فقط از IPهای
  Cloudflare درخواست می‌پذیرد)، یا در nginx ماژول realip را برای IPهای CDN تنظیم کنید تا `$remote_addr`
  همان IP بازدیدکننده شود.
- اگر IP را نمی‌خواهید بفرستید: `CLIENT_IP_HEADER=none` (آن‌وقت همهٔ مهمان‌ها در یک سهمیه‌اند).

### محدودیت نرخ به‌ازای IP روی مسیرهای کاتالوگ (پیشنهادی)

خواندن‌های عمومی کاتالوگ در کش داده‌های Next.js نگه داشته می‌شوند و بیشترشان بدون IP بازدیدکننده به API
می‌روند، پس هر کش‌نخوردن (miss) از سهمیهٔ مهمان مشترک **خود سرور فروشگاه** (`THROTTLE_ANON`) کم می‌شود.
فروشگاه دو سد دارد:

- پرس‌وجوهای «دم‌دراز» فهرست کالا (جستجو، حداقل یا حداکثر قیمت، `attribute_values` یا بیش از یک برند) IP
  بازدیدکننده را می‌فرستند: کش آن‌ها برای هر بازدیدکننده جداست و هزینهٔ هر miss از سهمیهٔ خود او کم می‌شود.
  فهرست‌های ساده (بدون پارامتر، یا فقط مرتب‌سازی، صفحه، گزینه‌های بله/خیر یا یک برند) مشترک می‌مانند.
- پاسخ ۴۰۴ خود API برای نامک (slug) کالا، دسته، برند و فهرست تا ۶۰ ثانیه در حافظهٔ هر پردازه نگه داشته
  می‌شود (حداکثر ۵۰۰ مورد)؛ نامک ناموجودِ تکراری درخواستی به API نمی‌فرستد.

با این حال کسی که با یک IP صفحه‌های ساختگیِ زیادی (نامک‌های ناموجودِ تازه، صفحه‌های بی‌شمار) باز کند
هنوز از سهمیهٔ مشترک خرج می‌کند. یک `limit_req` به‌ازای IP در nginx جلوی فروشگاه این را محدود می‌کند:

```nginx
# در سطح http (مثلاً بالای /etc/nginx/conf.d/<shop>.conf، بیرون از server):
limit_req_zone $binary_remote_addr zone=firefly_catalog:10m rate=10r/s;

# داخل server فروشگاه، پیش از `location /`:
location ~ ^/(product|product-category|brand|categories|search)/ {
    limit_req zone=firefly_catalog burst=60 nodelay;
    limit_req_status 429;
    proxy_pass http://firefly_storefront;
    proxy_buffering off;
}
```

- این `location` هیچ `proxy_set_header` یا `add_header` خودش را ندارد، پس هدرهای سطح `server` (از جمله
  `X-Real-IP` و HSTS) به آن به ارث می‌رسند. اگر چیزی از این دو اضافه کردید، همه را آنجا تکرار کنید.
- `burst` را بزرگ بگیرید: هر جابه‌جایی سمت کاربر و هر prefetch پیوندهای کارت‌ها در صفحهٔ فهرست هم یک
  درخواست به همین مسیرهاست. `rate=10r/s` و `burst=60` برای مرور عادی، حتی تند، کافی است.
- پشت CDN، `$binary_remote_addr` باید IP بازدیدکننده باشد (ماژول realip؛ بخش بالا)، وگرنه همهٔ کاربران
  پشت یک IP لبه شمرده می‌شوند.
- `/api/bff/` را در این قاعده نگذارید؛ سهمیهٔ مهمانِ آن به‌ازای IP بازدیدکننده در خود API حساب می‌شود.

## تنظیمات لازم در بک‌اند برای هر فروشگاه

همه فقط تنظیم env بک‌اند و پنل‌اند؛ تغییر کد لازم نیست.

| متغیر بک‌اند | مقدار | چرا |
| --- | --- | --- |
| `SITE_DOMAIN` | `shop.ir` (دامنهٔ **فروشگاه**، بدون `https://`) | آدرس صفحه‌ها و تصاویر در JSON-LD، `ALLOWED_HOSTS` و مقدار پیش‌فرض `STOREFRONT_URL` از آن ساخته می‌شود. |
| `STOREFRONT_URL` | `https://shop.ir` (بدون اسلش پایانی) | آدرس بازگشت بانک، لینک پرداخت سفارش، `<loc>` سایت‌مپ، خط `Sitemap:` در robots و پایهٔ لینک‌های کوتاه. |
| `EXTRA_ALLOWED_HOSTS` | `api.shop.ir` | فقط در حالت دامنه‌های جدا: میزبان API باید مجاز باشد. |
| `TRUSTED_PROXY_IPS` | IP سرور فروشگاه، و IP پروکسی جلوی API اگر هست | تا `X-Forwarded-For` فروشگاه پذیرفته شود (تطبیق دقیق، بدون CIDR). جزئیات پایین. |
| `TRUSTED_PROXY_HOPS` | `1` | پیش‌فرض؛ تغییر ندهید مگر بدانید چرا. |
| `GATEWAY_RESULT_URL_ALLOWED_HOSTS` | `shop.ir` | میزبان صفحهٔ نتیجهٔ پرداخت باید در این فهرست باشد. پیش‌فرض آن `SITE_DOMAIN` و میزبان `STOREFRONT_URL` است و معمولاً کافی است؛ اگر آن را دستی تنظیم کرده‌اید، میزبان فروشگاه را اضافه کنید. |
| `THROTTLE_ANON` | مثلاً `20000/hour` برای فروشگاه پربازدید | خواندن‌های عمومی کش‌شده (تنظیمات، منو، دسته‌ها…) بدون IP بازدیدکننده و همه با IP سرور فروشگاه می‌روند و یک سهمیهٔ مهمان مشترک دارند (پیش‌فرض `2000/hour` برای کل فروشگاه). پیش از راه‌اندازی و پیش از کمپین‌های پیامکی بزرگ (هر کلیک لینک کوتاه یک درخواست است) بالا ببرید؛ در صورت نیاز `THROTTLE_SEARCH_SUGGEST` و `THROTTLE_PAYMENT_STATUS` را هم. |
| `USE_HTTPS` و `DEBUG` | `True` و `False` | در تولید الزامی (پیش‌فرض `DEBUG` روشن است). |

در **پنل مدیریت** بک‌اند:

1. **کلید API:** «تنظیمات › کلید های دسترسی API» (فقط superuser) یک کلید برای این فروشگاه بسازید و در
   `FIREFLY_API_KEY` بگذارید. برای هر کلاینت (وب، اندروید، iOS) کلید جدا بسازید تا بتوان هر کدام را جدا
   غیرفعال کرد. کلید حذف‌شده برنمی‌گردد و غیرفعال‌کردن حداکثر ۶۰ ثانیه طول می‌کشد.
2. **آدرس نتیجهٔ پرداخت:** در «تنظیمات درگاه پرداخت» فیلد «آدرس نتیجهٔ پرداخت» را
   `https://<shop>/payment/callback/` بگذارید (با اسلش پایانی؛ مثلاً `https://shop.ir/payment/callback/`).
   بک‌اند بعد از بازگشت از بانک کاربر را با `?result=…&payment=…` به این صفحه می‌فرستد.
3. **ارسال کد یک‌بارمصرف:** «تنظیمات SMTP» الزامی است: ورود با کد، ثبت‌نام، بازیابی رمز عبور و تغییر
   ایمیل همه کد ایمیلی می‌فرستند و بدون SMTP سالم هر ارسال با `503 auth_otp_send_failed` («ارسال کد ممکن
   نشد») رد می‌شود؛ یعنی ثبت‌نام و بازیابی رمز عملاً بسته‌اند. پیامک («سرویس‌های پیامک» با یک حساب قابل
   استفاده و الگوی فعال کد یک‌بارمصرف در «الگوهای پیامک») و تلگرام («تنظیمات Telegram Gateway») اختیاری‌اند؛
   تا یکی از آن‌ها فعال نباشد، ثبت‌نام و ورود با کد برای شمارهٔ موبایل پیشنهاد نمی‌شود. پس از تنظیم، یک
   ارسال واقعی را آزمایش کنید (چک‌لیست staging پایین).
4. **ورود با گوگل:** در «تنظیمات ورود با گوگل» شناسه و کلید مخفی کلاینت را بگذارید و کلید را روشن کنید. در
   Google Cloud Console، در همان OAuth Client (نوع Web application) دامنهٔ **فروشگاه** را در «Authorized
   JavaScript origins» اضافه کنید (`https://shop.ir`، و `https://www.shop.ir` اگر هست)؛ وگرنه دکمهٔ گوگل
   خطای `origin_mismatch` می‌دهد. دکمه با Google Identity Services یک ID token می‌گیرد و «Authorized redirect
   URIs» لازم نیست.
5. **Firebase (اعلان وب):** مقادیر `FIREBASE_*` فروشگاه باید از **همان** پروژهٔ Firebase باشند که حساب سرویس
   (service account) بک‌اند برای ارسال از آن استفاده می‌کند؛ توکن ساخته‌شده در پروژهٔ دیگر در اولین ارسال با
   `SENDER_ID_MISMATCH` رد و دستگاه غیرفعال می‌شود ([CUSTOMIZATION.md](CUSTOMIZATION.md#اعلان-وب-firebase)).

بعد از تغییر `SITE_DOMAIN` یا `STOREFRONT_URL` در بک‌اند `python manage.py clear_site_cache` و برای بررسی
تنظیمات `python manage.py check --deploy` را اجرا کنید (مثلاً هشدار `firefly.W003` یعنی `TRUSTED_PROXY_IPS`
خالی است).

### `TRUSTED_PROXY_IPS` در دو حالت

بک‌اند فقط وقتی به `X-Forwarded-For` اعتماد می‌کند که آدرس مستقیم اتصال (`REMOTE_ADDR`) در
`TRUSTED_PROXY_IPS` باشد، و آن‌وقت ورودی شمارهٔ `TRUSTED_PROXY_HOPS` از **راست** را IP کاربر می‌داند.

- **فروشگاه مستقیم به Django وصل می‌شود:** IP سرور فروشگاه (همان‌طور که Django آن را می‌بیند) را در
  `TRUSTED_PROXY_IPS` بگذارید. اگر IP کانتینر عوض شود اعتماد بی‌صدا قطع می‌شود؛ IP را ثابت کنید.
- **بین فروشگاه و Django یک reverse proxy هست** (حالت معمول، مثلاً nginx روی `api.shop.ir`): اضافه‌کردن IP
  فروشگاه کافی نیست، چون آن پروکسی IP فروشگاه را به انتهای فهرست اضافه می‌کند. پروکسی API باید
  `X-Forwarded-For` فروشگاه را بپذیرد و Django به خود پروکسی اعتماد کند:

  ```nginx
  # nginx جلوی API (api.shop.ir)
  set_real_ip_from <IP سرور فروشگاه>;     # فقط از این آدرس
  real_ip_header X-Forwarded-For;
  real_ip_recursive on;

  location / {
      proxy_pass http://127.0.0.1:8000;
      proxy_set_header Host $host;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto https;
  }
  ```

  و در بک‌اند `TRUSTED_PROXY_IPS=<IP پروکسی API از دید Django>` (مثلاً `127.0.0.1`) به‌همراه IP سرور
  فروشگاه، با `TRUSTED_PROXY_HOPS=1`. این‌طور درخواست‌های اپ موبایل و هر کلاینت دیگری که مستقیم به API
  می‌آید هم IP درست خودشان را می‌گیرند و کسی نمی‌تواند IP جعل کند.

برای فهمیدن این‌که درخواست‌های فروشگاه از چه IPی می‌رسند، لاگ دسترسی nginx جلوی API را ببینید.

## نمودار استقرار (توپولوژی)

### الف) دامنه‌های جدا (پیشنهادی)

فروشگاه روی `shop.ir` و API روی `api.shop.ir`. بک‌اند: `SITE_DOMAIN=shop.ir`،
`STOREFRONT_URL=https://shop.ir`، `EXTRA_ALLOWED_HOSTS=api.shop.ir`. فروشگاه: `FIREFLY_API_URL=https://api.shop.ir`.

```
 Browser
    |  https://shop.ir   (pages, /api/bff/*, /media/*, /sitemap.xml, bank callback)
    v
 +-------------------------------+
 | nginx  shop.ir                |  TLS, gzip/brotli, X-Real-IP = $remote_addr
 +---------------+---------------+
                 |  http://127.0.0.1:3000
                 v
 +-------------------------------+   https://api.shop.ir/api/v1/...
 | Next.js storefront container  |   X-API-Key, X-Forwarded-For: <visitor IP>
 |  pages (SSR), BFF, proxy.ts   +-------------------------------------+
 +-------------------------------+   also forwards /media/ /static/      |
                                     /sitemap.xml and the bank callback  v
                                                    +-----------------------------------+
                                                    | nginx  api.shop.ir                |
                                                    |  realip: trust the storefront IP  |
                                                    +-----------------+-----------------+
                                                                      v
                                                    +-----------------------------------+
                                                    | Django  Firefly Core  (:8000)     |
                                                    |  TRUSTED_PROXY_IPS = API proxy IP |
                                                    +-----------------------------------+
```

- آدرس تصاویر در پاسخ‌های API به `api.shop.ir/media/…` اشاره می‌کند که برای مرورگر درست است.
- JSON-LD بک‌اند تصاویر را با `https://shop.ir/media/…` می‌سازد؛ فروشگاه این مسیر را به API می‌فرستد.
- مرورگر هرگز مستقیم API را صدا نمی‌زند؛ پس تنظیمات CORS بک‌اند برای فروشگاه مهم نیست.

### ب) یک دامنه (single origin)

فروشگاه و API هر دو روی `shop.ir` و یک nginx مسیرها را تقسیم می‌کند. بک‌اند: `SITE_DOMAIN=shop.ir`
(`STOREFRONT_URL` پیش‌فرض). فروشگاه و آرگومان ساخت: `FIREFLY_API_URL=https://shop.ir`.

```
 Browser
    |  https://shop.ir
    v
 +----------------------------------------------------------------+
 | nginx  shop.ir                                                 |
 |   /api/v1/  /sitemap.xml  /static/  /secureAccessPanel/  ------+--> Django (:8000)
 |   /media/   (alias to the media volume)  ----------------------+--> files on disk
 |   everything else  --------------------------------------------+--> Next.js (:3000)
 +----------------------------------------------------------------+
        ^                                                    |
        |   SSR and BFF call https://shop.ir/api/v1/...      |
        +----------------------------------------------------+
```

در این حالت `/api/v1/`، `/media/`، `/static/`، `/sitemap.xml` و پنل **باید** پیش از `location /` به Django
بروند؛ وگرنه فروشگاه آن‌ها را به همین دامنه، یعنی به خودش، برمی‌گرداند و حلقه درست می‌شود. Django با
`DEBUG=False` فایل‌های `/media/` را سرو نمی‌کند؛ nginx آن‌ها را از volume بخواند. بلوک کامل:

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name shop.ir;
    # TLS، فشرده‌سازی، هدرهای پروکسی و /_next/static/ مثل deploy/nginx.conf.example
    # و لاگ پوشانده: map‌ها و log_format firefly_masked همان فایل، در سطح http
    access_log /var/log/nginx/shop.access.log firefly_masked;

    # درخواست‌های SSR خود فروشگاه X-Forwarded-For بازدیدکننده را دارند: فقط از آدرس فروشگاه بپذیر.
    set_real_ip_from <آدرسی که درخواست‌های کانتینر فروشگاه از آن می‌رسند>;
    real_ip_header X-Forwarded-For;
    real_ip_recursive on;

    location /api/v1/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
    }
    location = /sitemap.xml      { proxy_pass http://127.0.0.1:8000; proxy_set_header Host $host; }
    location /static/            { proxy_pass http://127.0.0.1:8000; proxy_set_header Host $host; }
    location /secureAccessPanel/ { proxy_pass http://127.0.0.1:8000; proxy_set_header Host $host; }
    location /ckeditor/          { proxy_pass http://127.0.0.1:8000; proxy_set_header Host $host; }
    location /media/ {
        alias /srv/firefly/media/;
        add_header X-Content-Type-Options nosniff;
        add_header Content-Security-Policy "default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; sandbox";
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Accept-Encoding "";   # nginx فشرده می‌کند
        proxy_buffering off;
    }
}
```

و در بک‌اند `TRUSTED_PROXY_IPS=127.0.0.1` (آدرس همین nginx از دید Django).

## بررسی سلامت

فروشگاه مسیر `/healthz/` را دارد که سلامت خود سرور را نشان می‌دهد: متغیرهای محیطی را اعتبارسنجی می‌کند و
اگر درست باشند `200` با متن `ok` می‌دهد؛ اگر متغیر الزامی تنظیم نشده یا مقداری نامعتبر باشد `503` با متن
`unhealthy` (بدون جزئیات در پاسخ؛ فهرست متغیرهای نامعتبر، فقط نام و قاعده، یک بار با
`[healthz] unhealthy:` در لاگ می‌آید). پاسخ کش نمی‌شود و **هیچ درخواستی به API نمی‌فرستد** (تنظیمات و پوستهٔ
فروشگاه هم بار نمی‌شوند). پس قطع‌شدن بک‌اند کانتینر را unhealthy نمی‌کند و باعث راه‌اندازی دوبارهٔ
بی‌فایدهٔ آن نمی‌شود، ولی کانتینری با env اشتباه سالم گزارش نمی‌شود. اسلش پایانی را بگذارید: `/healthz`
بدون اسلش یک ریدایرکت ۳۰۸ به `/healthz/` است.

ایمیج یک `HEALTHCHECK` دارد که هر ۳۰ ثانیه همین مسیر را با `wget` صدا می‌زند:

```bash
docker inspect --format '{{.State.Health.Status}}' shop-front   # healthy | unhealthy | starting
curl -i https://shop.ir/healthz/                                 # 200 ok (یا 503 unhealthy: env)
```

برای load balancer و پایش (uptime monitor) هم `/healthz/` را بگذارید، نه صفحهٔ اصلی (که کل پوسته را رندر
می‌کند و به API وابسته است). نمونهٔ nginx این مسیر را بدون لاگ دسترسی می‌فرستد. Docker کانتینر unhealthy را
خودش دوباره راه نمی‌اندازد؛ وضعیت را پایش کنید.

اتصال به **API** را جداگانه بسنجید: `curl -i https://shop.ir/robots.txt` باید `200` بدهد (robots.txt از پنل
می‌آید و ۵ دقیقه کش می‌شود). `503` با `Retry-After: 300` یعنی API در دسترس نیست و نسخهٔ کش‌شده‌ای هم نیست
(موتورهای جستجو این را «موقتاً خزش نکن» می‌فهمند)؛ `500` معمولاً یعنی env نامعتبر است (`docker logs shop-front`).

## آزمون‌ها و CI

- **CI** (`.github/workflows/ci.yml`) روی هر push و pull request به `main` دو کار موازی دارد:
  - نصب، `typecheck`، `lint`، `format:check`، `test` و `build`؛
  - ساخت ایمیج Docker (با `docker/build-push-action`، بدون push)، اجرای آن با متغیرهای ساختگی ولی معتبر و
    بررسی `/healthz/` (پاسخ ۲۰۰ و وضعیت `healthy` در `docker inspect`)، و یک کانتینر بدون متغیرهای الزامی
    که باید ۵۰۳ بدهد.

  هیچ‌کدام به بک‌اند نیاز ندارند.
- **آزمون‌های end-to-end در CI اجرا نمی‌شوند**، چون بک‌اند با دادهٔ نمونه (مخزن جدا) لازم دارند. پیش از هر
  push، روی سیستم خودتان با بک‌اند نمونه روی `http://localhost:8000` اجرا کنید:

  ```bash
  pnpm test:e2e      # Playwright خودش build می‌کند و سرور standalone را بالا می‌آورد
  ```

  Playwright همان خروجی تولید را آزمایش می‌کند (`pnpm build` و سپس `pnpm start:standalone`، یعنی
  `server.js` خروجی standalone مثل داخل ایمیج) در سه اندازه: موبایل، تبلت و دسکتاپ. اگر سروری روی
  `http://localhost:3000` در حال اجراست همان استفاده می‌شود؛ پیش از اجرا مطمئن شوید نسخهٔ قدیمی نیست. با
  `E2E_BASE_URL` می‌توانید آدرس دیگری بدهید. سرور دومی هم روی `http://localhost:3001` (یا
  `E2E_PUSH_BASE_URL`) با همان build و مقدارهای ساختگی `FIREBASE_*` بالا می‌آید تا بودجهٔ جاوااسکریپت
  فروشگاهی که اعلان وب دارد هم سنجیده شود (پروژهٔ `budget-push`)؛ این مقدارها هیچ درخواستی به Firebase
  نمی‌فرستند.

  **سهمیهٔ بک‌اند.** هر اجرای کامل حدود ۱٬۹۰۰ درخواست به API می‌فرستد که حدود **۷۰۰** تای آن‌ها ناشناس‌اند،
  همه از یک نشانی؛ سقف پیش‌فرض بک‌اند نمونه ۲۰۰۰ درخواست ناشناس در ساعت است (`THROTTLE_ANON`، یک ساعت
  لغزان). پس **حداکثر دو اجرای کامل در ساعت** جا می‌شود (با مرور دستی کمتر)؛ اجرای سوم وسط کار به 429
  می‌خورد و بسیاری از آزمون‌ها با هم شکست می‌خورند. Playwright پیش از شروع دو کار می‌کند
  (`tests/e2e/global-setup.ts`): یک خواندن ناشناس از بک‌اند، که اگر پاسخ 429 باشد اجرا را با زمان انتظار
  متوقف می‌کند؛ و دفتری از شروع اجراهای کامل همین دستگاه (`tests/e2e/.state/full-runs.json`) که اگر دو اجرای
  کامل در ساعت گذشته شروع شده باشد، اجرای تازه را بی‌درنگ با «Wait N s» متوقف می‌کند. اجرای فیلترشده (یک فایل،
  یک پروژه، `-g`) در دفتر نوشته نمی‌شود. برای اجراهای پشت‌سرهم بک‌اند را با سقف بزرگ‌تر بالا بیاورید، مثلاً
  `THROTTLE_ANON=20000/hour`، و `E2E_SKIP_ANON_LEDGER=1` بگذارید.

  **نوشتن در پایگاه دادهٔ نمونه.** سفارش‌ها در بک‌اند نمونه ماندگارند و خرج کیف پول واقعی است؛ پس آزمون‌های
  سفارش و پول با حساب‌های shirin (کیف پول) و k.yazdi و با مهمان اجرا می‌شوند، هرگز با sara (پیشخوان او را
  آزمون‌های دیگر می‌خوانند)، و هر چه را عوض می‌کنند برمی‌گردانند. یک اجرای کامل عادی: ۶ سفارش ثبت و هر ۶ لغو
  (۴ مهمان، ۲ k.yazdi)، ۸ درخواست پرداخت (۲ کارت‌به‌کارت باز و لغو، ۶ ردشده از بانک نمونه)، یک کد تخفیف
  (TEA30 یا FREESHIP، هر کدام که هنوز معتبر است)، ۷ پیگیری سفارش، ۲ «خرید دوباره» (سبدها برمی‌گردند)، یک
  شارژ کیف پول که بانک نمونه رد می‌کند و یک درخواست برداشت که ثبت و لغو می‌شود (shirin؛ موجودی بی‌تغییر)، و
  ۲۹ ورود و خروج (`auth_attempt`، حداکثر ۲۰ در دقیقه). هیچ رسیدی بارگذاری و هیچ پولی خرج نمی‌شود؛ سبدها و
  دفترچهٔ آدرس‌ها دقیقاً برمی‌گردند.

  **متغیرهای اختیاری:**

  | متغیر | کار | هزینه در پایگاه دادهٔ نمونه |
  | --- | --- | --- |
  | `E2E_LIVE_RECEIPT=1` | رسید کارت‌به‌کارت را واقعاً بارگذاری می‌کند (در اجرای عادی پاسخ آن ساختگی است). | هر اجرا یک سفارش مهمان «در انتظار بررسی» با یک تصویر رسید می‌ماند که لغوشدنی نیست؛ اپراتور رسید را رد کند. |
  | `E2E_LIVE_WALLET_ORDER=1` | shirin یک سفارش را کامل از کیف پولش می‌پردازد. | هر اجرا حدود ۲۶۸٬۰۰۰ تومان از کیف پول shirin برای همیشه خرج می‌شود و یک سفارش «در حال انجام» می‌ماند. |
  | `E2E_COUPONS=کد۱,کد۲` | جای کدهای نمونه (TEA30، سپس FREESHIP) را در خرید مهمان می‌گیرد؛ برای آزمودن حالت‌های جایگزین با کدهایی که API واقعاً رد می‌کند. | هزینه‌ای جز همان اعمال یا رد کدها ندارد. |
  | `E2E_SKIP_ANON_LEDGER=1` | دفتر اجراهای کامل را نادیده می‌گیرد (وقتی سهمیه آزاد است، مثلاً با `THROTTLE_ANON` بزرگ‌تر). | هیچ؛ اما اجرای سوم در ساعت ممکن است به 429 بخورد. |

## چک‌لیست راه‌اندازی و به‌روزرسانی

### راه‌اندازی فروشگاه جدید

- [ ] بک‌اند: `SITE_DOMAIN`، `STOREFRONT_URL`، (`EXTRA_ALLOWED_HOSTS`)، `TRUSTED_PROXY_IPS`،
      `GATEWAY_RESULT_URL_ALLOWED_HOSTS`، `THROTTLE_ANON`، `USE_HTTPS=True`، `DEBUG=False`؛ سپس
      `clear_site_cache` و `check --deploy`.
- [ ] پنل: کلید API برای فروشگاه و «آدرس نتیجهٔ پرداخت» = `https://<shop>/payment/callback/`؛ «تنظیمات
      SMTP» (کد یک‌بارمصرف)؛ اگر لازم است پیامک، تلگرام و ورود با گوگل (دامنهٔ فروشگاه در «Authorized
      JavaScript origins»).
- [ ] اعلان وب: `FIREBASE_*` از همان پروژهٔ Firebase حساب سرویس بک‌اند.
- [ ] [آزمون روی staging](#آزمون-روی-staging-پیش-از-راه‌اندازی) برای مسیرهای ورود، ثبت‌نام، حساب و اعلان.
- [ ] ساخت ایمیج با `--build-arg FIREFLY_API_URL=<آدرس عمومی API>`.
- [ ] فایل env از روی `.env.example` (`FIREFLY_API_URL`، `FIREFLY_API_KEY`، `SITE_URL` و ظاهر).
- [ ] اجرای کانتینر روی `127.0.0.1` و nginx با گواهی TLS؛ `nginx -t` و reload.
- [ ] بررسی: `curl -i https://<shop>/healthz/` ← ۲۰۰ `ok` و `docker inspect` ← `healthy`؛
      `curl -i https://<shop>/robots.txt` ← ۲۰۰ (اتصال به API)؛ صفحهٔ اصلی با لوگو و منوها؛ یک تصویر محصول
      بهینه‌شده (`/_next/image/?url=…` با ۲۰۰)؛ `curl -i https://<shop>/sitemap.xml` ← ۲۰۰.
- [ ] بازگشت بانک: `curl -i -X POST https://<shop>/api/v1/payment/gateway/callback/<gateway>/<token>/`
      باید ۳۰۲ بدهد (به صفحهٔ نتیجه)، نه ۳۰۱ یا ۵۰۰.

### آزمون روی staging پیش از راه‌اندازی

محیط توسعه SMTP، پیامک، تلگرام، گوگل، Firebase و کلید نشان ندارد؛ این مسیرها فقط با پاسخ‌های ساختگی آزموده
شده‌اند. روی staging با همان تنظیمات تولید و یک حساب آزمایشی (نه حساب مشتری واقعی) یک بار هر کدام را انجام
دهید:

- [ ] ورود با کد: کد ایمیلی (و پیامک یا تلگرام اگر فعال است) می‌رسد، شمارش معکوس و «ارسال مجدد کد» درست است
      و ورود انجام می‌شود.
- [ ] ثبت‌نام با ایمیل (و با شمارهٔ موبایل اگر فعال است): کد، رمز عبور، ورود خودکار و سبد مهمان ادغام‌شده.
- [ ] بازیابی رمز عبور: کد، رمز تازه، بازگشت به صفحهٔ ورود با شناسهٔ پرشده و ورود با رمز تازه.
- [ ] ورود با گوگل: دکمه نمایش داده می‌شود، پنجرهٔ گوگل باز می‌شود (بدون `origin_mismatch`) و ورود انجام
      می‌شود؛ برای حساب تازه، ثبت‌نام.
- [ ] تغییر ایمیل و شمارهٔ موبایل در «اطلاعات حساب»: کد به ایمیل یا شمارهٔ تازه می‌رسد و تأیید می‌شود.
- [ ] ورود دومرحله‌ای: فعال‌سازی با QR در یک اپ احراز هویت، ورود با کد آن، و غیرفعال‌سازی.
- [ ] بارگذاری و حذف تصویر پروفایل (تا ۵ مگابایت).
- [ ] اعلان وب: روشن‌کردن در «اعلان‌ها»، دریافت یک اعلان آزمایشی از پنل، کلیک روی آن (صفحهٔ «اعلان‌ها» باز
      می‌شود)، خاموش‌کردن، و خروج از حساب (دستگاه از کار می‌افتد).
- [ ] نقشهٔ نشان: در «آدرس‌های من» «انتخاب موقعیت روی نقشه»؛ کاشی‌ها و لوگوی نشان می‌آیند و جستجوی آدرس
      کار می‌کند.

### به‌روزرسانی نسخه

- [ ] تغییرات را بخوانید و `.env.example` را با نسخهٔ قبل مقایسه کنید (`git diff <قبلی>..HEAD -- .env.example`):
      متغیر جدید را به فایل env اضافه کنید.
- [ ] روی سیستم خودتان `pnpm test` و `pnpm test:e2e` را با بک‌اند نمونه اجرا کنید؛ CI باید سبز باشد.
- [ ] ایمیج جدید را با **همان** `FIREFLY_API_URL` و یک برچسب تازه بسازید (برچسب قبلی را برای بازگشت نگه
      دارید).
- [ ] کانتینر جدید را روی پورت دیگری بالا بیاورید، `/healthz/` (سلامت و env)، `/robots.txt` (اتصال به API) و
      صفحهٔ اصلی را بررسی کنید، سپس upstream nginx را عوض کنید (یا کانتینر قدیمی را متوقف و جدید را روی همان
      پورت اجرا کنید).
- [ ] بعد از راه‌اندازی، کش داده خالی است و چند دقیقهٔ اول درخواست بیشتری به API می‌رود؛ طبیعی است.
- [ ] بازگشت: کانتینر را با برچسب قبلی دوباره اجرا کنید.
- [ ] تغییر نسخهٔ Node: `.nvmrc` و `NODE_VERSION` در Dockerfile را با هم عوض کنید (حداقل ۲۲.۱۲).

## دربارهٔ CSP

فروشگاه فعلاً فقط `Content-Security-Policy: frame-ancestors 'self'` را می‌فرستد (جلوگیری از نمایش در
iframe سایت‌های دیگر؛ بخش nginx را ببینید) و برای اسکریپت و استایل سیاستی ندارد. اگر بعداً CSP کامل
اضافه کنید، باید **مبتنی بر nonce** باشد (و `frame-ancestors` را نگه دارد)، چون این‌ها اسکریپت و استایل
درون‌خطی دارند:

- اسکریپت‌های درون‌خطی خود Next.js (دادهٔ RSC)؛
- یک اسکریپت کوچک درون‌خطی برای هر اطلاعیهٔ نوار بالا (به‌خاطر سپردن بسته‌شدن آن پیش از نمایش)؛
- کدهای اسنیپت اپراتور (آنالیتیکس، نماد اعتماد و…) که هم درون‌خطی‌اند و هم از دامنه‌های دیگر بار می‌شوند؛
- تگ `<style>` تم که رنگ‌ها را در زمان اجرا می‌نویسد.

در آن صورت `proxy.ts` باید برای هر درخواست یک nonce بسازد و در هدر CSP بگذارد؛ Next.js آن را روی
اسکریپت‌های خودش می‌گذارد و اسنیپت‌ها، اسکریپت اطلاعیه و استایل تم هم باید همان nonce را بگیرند (صفحه‌ها
همین حالا پویا هستند، پس nonce به‌ازای هر درخواست ممکن است). `'unsafe-inline'` عملاً CSP را بی‌اثر می‌کند. دامنه‌های سرویس‌های اسنیپت (مثلاً گوگل آنالیتیکس،
eNamad) را هم در `script-src`، `img-src` و `connect-src` مجاز کنید.
