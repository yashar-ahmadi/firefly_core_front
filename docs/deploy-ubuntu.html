پیش از شروع

این راهنما فرانت‌اند فروشگاه را روی یک سرور اوبونتوی تازه راه می‌اندازد و به سایتی با دامنهٔ خودش و HTTPS می‌رساند. فروشگاه داخل Docker اجرا می‌شود و nginx جلوی آن قرار می‌گیرد. همهٔ کارهای تکراری، یعنی ساخت ایمیج، جابه‌جایی نسخه‌ها و نوشتن پیکربندی nginx، با اسکریپت deploy/ubuntu/firefly.sh در خود مخزن انجام می‌شود.

  • مرورگربازدیدکنندهٔ فروشگاه
  • nginxHTTPS، فشرده‌سازی و لاگ بدون اطلاعات پرداخت
  • کانتینر فروشگاهنسخهٔ «آبی» یا «سبز»، فقط روی 127.0.0.1
  • API فایرفلایبک‌اند، روی سرور خودش

هر فروشگاه دو جایگاه دارد که «آبی» و «سبز» نام گرفته‌اند و هر کدام پورت محلی خودش را دارد. در هر به‌روزرسانی، نسخهٔ تازه در جایگاه خالی بالا می‌آید و سلامتش بررسی می‌شود. پس از آن nginx به آن منتقل می‌شود و نسخهٔ قبلی، بعد از تمام شدن درخواست‌های در جریانش، خاموش می‌شود. اگر نسخهٔ تازه سالم بالا نیاید، سایت روی همان نسخهٔ قبلی می‌ماند.

آنچه این راهنما پوشش نمی‌دهد

استقرار بک‌اند فایرفلای (Django) موضوع این راهنما نیست. پیش از شروع، API باید روی یک نشانی عمومی HTTPS، مثلاً https://api.shop.ir، در دسترس باشد. تنظیماتی که بک‌اند برای هر فروشگاه لازم دارد در بخش «تنظیمات بک‌اند» آمده است.

در مثال‌های این راهنما نام فروشگاه digital، دامنهٔ آن shop.ir و نشانی API https://api.shop.ir است. این‌ها را با مقدارهای خودتان عوض کنید.

پیش‌نیازها

موردحداقل و پیشنهاد
سیستم‌عاملاوبونتو ۲۶٫۰۴ LTS (پیشنهادی) یا اوبونتو ۲۴٫۰۴ LTS، نسخهٔ ۶۴ بیتی. هر دو را Docker رسماً پشتیبانی می‌کند و اسکریپت تفاوت nginx آن‌ها را خودش در نظر می‌گیرد.
پردازنده و حافظهدست‌کم ۲ هسته و ۲ گیگابایت رم برای یک فروشگاه، به‌علاوهٔ ۲ گیگابایت swap. برای چند فروشگاه روی یک سرور، ۴ گیگابایت رم یا بیشتر.
دیسکدست‌کم ۲۰ گیگابایت فضای خالی. هر ایمیج حدود ۳۵۰ مگابایت است و اسکریپت برای هر فروشگاه سه نسخهٔ آخر را نگه می‌دارد. حافظهٔ موقت ساخت Docker هم فضا می‌گیرد.
دامنهدسترسی به تنظیمات DNS دامنهٔ فروشگاه، برای ساخت رکورد A.
بک‌اندAPI فایرفلای روی نشانی عمومی HTTPS، و دسترسی superuser به پنل آن برای ساخت کلید API.
دسترسیورود با SSH و کاربری که اجازهٔ sudo دارد.

ایمیج فروشگاه روی خود سرور ساخته می‌شود. در آزمایش ما روی سروری با ۴ هستهٔ پردازنده، ساخت حدود دو تا سه دقیقه طول کشید و در همین مدت حدود یک گیگابایت رم مصرف شد. کانتینر در حال کار، در حالت بیکار، حدود ۸۰ مگابایت رم می‌گیرد. زیر بار و هنگام بهینه‌سازی تصاویر این عدد بالاتر می‌رود، پس برای هر فروشگاه دست‌کم یک گیگابایت رم کنار بگذارید.

آماده‌سازی سرور

به‌روزرسانی بسته‌ها

با SSH وارد سرور شوید و بسته‌ها را به‌روز کنید:

دیوار آتش (ufw)

فقط سه پورت باید از بیرون باز باشد: SSH، و ۸۰ و ۴۴۳ برای وب.

هشدار

قاعدهٔ SSH را پیش از ufw enable اضافه کنید، وگرنه ارتباط فعلی‌تان قطع می‌شود و دیگر نمی‌توانید وارد سرور شوید. اگر SSH روی پورت دیگری است، همان پورت را باز کنید، مثلاً sudo ufw allow 2222/tcp.

طبق مستندات Docker، پورتی که Docker برای یک کانتینر روی همهٔ نشانی‌های سرور منتشر کند از قاعده‌های ufw عبور می‌کند. اسکریپت این راهنما کانتینرها را فقط روی 127.0.0.1 منتشر می‌کند، پس از بیرون در دسترس نیستند. دلیل این کار امنیتی است: برنامه به هدر X-Real-IP که nginx می‌فرستد اعتماد می‌کند، پس پورت کانتینر هرگز نباید رو به اینترنت باشد.

نصب Docker

نکته

اگر سرور در ایران است و hello-world با خطای دسترسی یا 403 متوقف شد، پیش از ادامه بخش بعد را انجام دهید.

سرور داخل ایران

ساخت ایمیج به دو منبع خارجی نیاز دارد: ایمیج پایهٔ node:22.23-alpine از Docker Hub، و بسته‌های npm از registry.npmjs.org. از سرورهای داخل ایران ممکن است دسترسی به یکی یا هر دو محدود باشد. هر دو را می‌توان به mirror سپرد. نشانی mirror را از ارائه‌دهندهٔ سرور یا منبعی که به آن اعتماد دارید بگیرید.

طبق مستندات Docker، این تنظیم فقط برای ایمیج‌های Docker Hub به کار می‌رود، که ایمیج پایهٔ فروشگاه هم از همین دسته است.

راه جایگزین: ساخت ایمیج بیرون از سرور

اگر mirror در دسترس نیست، ایمیج را روی سیستمی که به اینترنت آزاد دسترسی دارد بسازید و به سرور منتقل کنید. نام ایمیج باید با firefly-front/ و نام فروشگاه شروع شود و FIREFLY_API_URL همان مقدار فایل تنظیمات فروشگاه باشد:

دستور rollback همراه با نام یک نسخه، فروشگاه را به هر نسخه‌ای که روی سرور هست منتقل می‌کند، با همان روش بی‌وقفه‌ای که در به‌روزرسانی عادی به کار می‌رود.

دریافت کد پروژه

کد در /opt/firefly-front قرار می‌گیرد. مخزن خصوصی است، پس سرور یک کلید SSH فقط‌خواندنی (Deploy key) می‌گیرد:

  1. یک کلید مخصوص استقرار بسازید و کلید عمومی آن را نمایش دهید:

  2. در GitHub به صفحهٔ مخزن بروید و از Settings بخش Deploy keys را باز کنید. روی Add deploy key بزنید، یک عنوان بنویسید (مثلاً نام سرور) و خروجی دستور قبل را در کادر کلید بگذارید. گزینهٔ Allow write access را خاموش بگذارید؛ سرور فقط کد را می‌خواند.

  3. مخزن را با همین کلید دریافت کنید و کلید را در تنظیمات مخزن ثبت کنید تا دستور git pull در به‌روزرسانی‌های بعدی هم از آن استفاده کند:

    در اولین اتصال، SSH اثر انگشت GitHub را نشان می‌دهد و تأیید می‌خواهد؛ yes بنویسید.

تنظیمات بک‌اند فایرفلای

این تنظیمات روی سرور بک‌اند و در پنل مدیریت آن انجام می‌شود، نه روی سرور فروشگاه. بدون آن‌ها صفحه‌ها بالا می‌آیند، اما پرداخت، سایت‌مپ یا سهمیهٔ درخواست مهمان‌ها درست کار نمی‌کند. توضیح کامل هر مورد در docs/DEPLOYMENT.md آمده است.

متغیر بک‌اندمقدار نمونهکاربرد
SITE_DOMAINshop.irدامنهٔ فروشگاه، بدون https://
STOREFRONT_URLhttps://shop.irبازگشت از بانک، لینک پرداخت، سایت‌مپ و لینک‌های کوتاه
EXTRA_ALLOWED_HOSTSapi.shop.irمجاز کردن دامنهٔ API
TRUSTED_PROXY_IPSIP سرور فروشگاهتا بک‌اند IP واقعی بازدیدکننده را که فروشگاه می‌فرستد بپذیرد
THROTTLE_ANON20000/hourسقف درخواست مهمان‌ها؛ همهٔ خواندن‌های کش‌شدهٔ فروشگاه از یک IP می‌آیند
USE_HTTPS و DEBUGTrue و Falseالزامی در محیط تولید

در پنل مدیریت بک‌اند:

  • در «تنظیمات › کلید های دسترسی API» یک کلید برای این فروشگاه بسازید. این کلید در FIREFLY_API_KEY قرار می‌گیرد.
  • در «تنظیمات درگاه پرداخت»، «آدرس نتیجهٔ پرداخت» را https://shop.ir/payment/callback/ بگذارید، با اسلش پایانی.
  • «تنظیمات SMTP» را کامل کنید. ورود با کد، ثبت‌نام و بازیابی رمز عبور کد ایمیلی می‌فرستند و بدون SMTP سالم کار نمی‌کنند.

بعد از تغییر این مقادیر، روی سرور بک‌اند python manage.py clear_site_cache و برای بررسی python manage.py check --deploy را اجرا کنید.

فایل تنظیمات فروشگاه

هر فروشگاه یک فایل تنظیمات در /etc/firefly دارد. دستور init این فایل را از روی .env.example مخزن می‌سازد، چند تنظیم مخصوص اسکریپت را به انتهایش اضافه می‌کند و دسترسی آن را فقط به root می‌دهد:

نام فروشگاه فقط حروف کوچک انگلیسی، رقم و خط تیره می‌پذیرد. این مقدارها را حتماً تنظیم کنید:

متغیرنمونهتوضیح
FIREFLY_API_URLhttps://api.shop.irنشانی عمومی API. نشانی داخلی یا localhost پذیرفته نمی‌شود، چون نشانی تصاویر از همین مقدار ساخته می‌شود و localhost داخل کانتینر به خود کانتینر اشاره دارد.
FIREFLY_API_KEYکلیدی که در پنل ساختیدفقط سمت سرور می‌ماند و به مرورگر نمی‌رود.
SITE_URLhttps://shop.irنشانی عمومی فروشگاه، با https:// و بدون www. نسخهٔ www را nginx به همین نشانی منتقل می‌کند.
STORE_PRESETdigitalنوع فروشگاه: default، digital، agro، boardgame، carpet یا paint.

رنگ‌ها، فونت، نقشهٔ نشان، اعلان وب و امکانات جانبی در همین فایل تنظیم می‌شوند و توضیح هر کدام در docs/CUSTOMIZATION.md آمده است. رنگ‌ها را حتماً داخل کوتیشن بنویسید، مثل THEME_PRIMARY="#2563EB"؛ در این فایل‌ها # بدون کوتیشن شروع توضیح حساب می‌شود.

تنظیم‌های انتهای فایل را فقط اسکریپت می‌خواند:

تنظیمپیش‌فرضکاربرد
DEPLOY_PORT_BLUE و DEPLOY_PORT_GREEN3000 و 3001پورت‌های محلی دو جایگاه. init برای هر فروشگاه تازه جفت آزاد بعدی را انتخاب می‌کند (۳۰۱۰ و ۳۰۱۱، و به همین ترتیب).
DEPLOY_CACHE_SIZE512mسقف کش داده در حافظه. Next.js این کش را هیچ‌وقت خودش پاک نمی‌کند، پس اسکریپت آن را روی tmpfs با اندازهٔ محدود می‌گذارد.
DEPLOY_MEMORYخاموشسقف اختیاری حافظهٔ کانتینر، مثلاً 1g.
DEPLOY_NPM_REGISTRYخاموشنشانی mirror رجیستری npm برای ساخت (بخش «سرور داخل ایران»).
DEPLOY_KEEP_RELEASES3تعداد نسخه‌هایی که برای بازگشت روی سرور می‌مانند.
DEPLOY_DRAIN_SECONDS10مهلتی که نسخهٔ قبلی، بعد از جابه‌جایی، برای تمام کردن درخواست‌هایش دارد.
هشدار

این فایل کلید API را دارد. آن را در مخزن کامیت نکنید و دسترسی‌اش را (600، فقط root) تغییر ندهید.

اولین استقرار

این دستور چهار کار انجام می‌دهد:

  1. تنظیمات را بررسی می‌کند. اگر FIREFLY_API_URL به localhost اشاره کند یا SITE_URL نشانی HTTPS نباشد، پیش از هر کاری متوقف می‌شود.
  2. ایمیج را از کد همین پوشه می‌سازد. نام نسخه شامل زمان ساخت و شناسهٔ کامیت است، مثل firefly-front/digital:20261025-102640-1fce5ae476e1.
  3. کانتینر را در جایگاه آبی روی 127.0.0.1:3000 اجرا می‌کند و تا دو دقیقه منتظر می‌ماند تا /healthz/ پاسخ ۲۰۰ بدهد.
  4. نشانی /robots.txt را می‌خواند تا ارتباط با API را بسنجد. اگر پاسخ ۲۰۰ نباشد، هشدار می‌دهد ولی استقرار را برنمی‌گرداند.

در اولین اجرا، چون nginx هنوز تنظیم نشده، اسکریپت این را هم اعلام می‌کند. برای بررسی وضعیت:

پاسخ 200 با متن ok یعنی برنامه سالم است و متغیرهای محیطی معتبرند. وقتی کانتینر سالم بالا نیاید، اسکریپت آخرین سطرهای لاگ آن را چاپ می‌کند؛ بخش «عیب‌یابی» را ببینید.

اسکریپت پیکربندی را از deploy/nginx.conf.example مخزن می‌سازد و دو فایل در /etc/nginx/conf.d می‌نویسد:

  • فایل firefly-http.conf: بخش مشترک همهٔ فروشگاه‌ها، شامل قالب لاگی که توکن‌های پرداخت را از نشانی‌ها حذف می‌کند و هدر Vary نسخه‌های آفلاین.
  • فایل firefly-digital.conf: بخش مخصوص این فروشگاه، شامل HTTPS، انتقال www و http به https://shop.ir، فشرده‌سازی، کش یک‌سالهٔ فایل‌های ثابت، هدر HSTS، سقف ۶ مگابایت برای آپلود رسید و ارسال جریانی صفحه‌ها.

پورتی که nginx به آن وصل می‌شود در فایل جداگانهٔ /etc/nginx/firefly/digital.upstream است و در هر جابه‌جایی نسخه فقط همین فایل عوض می‌شود. nginx نسخهٔ ۲۴٫۰۴ (۱٫۲۴) دستور http2 on را نمی‌شناسد؛ اسکریپت نسخهٔ nginx را می‌خواند و در این حالت شکل قدیمی listen 443 ssl http2 را می‌نویسد.

اسکریپت در هر اجرا فایل‌های conf.d را بازنویسی می‌کند. برای تغییر پیکربندی، فایل نمونه در مخزن را ویرایش کنید و دستور nginx را دوباره اجرا کنید.

تمدید خودکار گواهی

بستهٔ certbot اوبونتو یک تایمر systemd نصب می‌کند که گواهی را پیش از انقضا تمدید می‌کند. --deploy-hook بالا ذخیره می‌شود و بعد از هر تمدید nginx را reload می‌کند. برای اطمینان:

بررسی نهایی

  • نشانی /healthz/ پاسخ 200 و متن ok می‌دهد و هدر strict-transport-security دارد.
  • نشانی /robots.txt پاسخ 200 می‌دهد. این یعنی فروشگاه به API وصل است و کلید درست است.
  • نشانی /sitemap.xml پاسخ 200 می‌دهد و نشانی‌هایش با https://shop.ir شروع می‌شوند.
  • نشانی http://www.shop.ir/ به https://shop.ir/ منتقل می‌شود.
  • مسیر بازگشت بانک پاسخ 302 می‌دهد، نه 301 یا 500. در دستور بالا به‌جای <gateway> نام یکی از درگاه‌های فعال فروشگاه را بنویسید.
  • در مرورگر، صفحهٔ اصلی با لوگو و منوها، یک صفحهٔ محصول با تصویر، سبد خرید و صفحهٔ ورود درست نمایش داده می‌شوند.

ما این روند را با nginx واقعی و درخواست‌های پشت‌سرهم آزمودیم. در چهار جابه‌جایی و حدود ۱۲۶۰ درخواست، هیچ پاسخ ۵۰۲ یا خطای برنامه دیده نشد. فقط دو اتصال تازه که دقیقاً هم‌زمان با reload باز شده بودند بسته شدند. این رفتار reload خود nginx است و با reload معمولی، مثلاً بعد از تمدید گواهی، هم پیش می‌آید.

اگر نسخهٔ تازه در دو دقیقه سالم نشود یا nginx پیکربندی را نپذیرد، اسکریپت کانتینر تازه را حذف می‌کند و سایت روی نسخهٔ قبلی می‌ماند. بعد از هر استقرار موفق، ایمیج‌های قدیمی‌تر از DEPLOY_KEEP_RELEASES نسخهٔ آخر پاک می‌شوند.

بعد از تغییر فایل تنظیمات

متغیرها هنگام ساخت کانتینر خوانده می‌شوند. بعد از ویرایش /etc/firefly/digital.env، دستور deploy را دوباره اجرا کنید. وقتی کد تغییر نکرده باشد، Docker از کش ساخت استفاده می‌کند و کل کار چند ثانیه طول می‌کشد.

نگهداری روزمره

لاگ‌ها

لاگ هر کانتینر حداکثر پنج فایل ده‌مگابایتی است و Docker قدیمی‌ترها را خودش حذف می‌کند. خود برنامه در محیط تولید هیچ لاگ درخواستی نمی‌نویسد.

هشدار

لاگ خطای nginx (error.log) را نمی‌توان پوشاند. اگر درخواستی به برنامه نرسد (مثلاً ۵۰۲)، خط کامل درخواست، که ممکن است توکن پرداخت داشته باشد، در آن نوشته می‌شود. دسترسی به این فایل را محدود نگه دارید. راه حذف این سطرها در docs/DEPLOYMENT.md، بخش «لاگ خطا بدون کلید پرداخت»، آمده است.

فضای دیسک

اسکریپت ایمیج‌های قدیمی هر فروشگاه را پاک می‌کند، ولی حافظهٔ موقت ساخت Docker به مرور بزرگ می‌شود. وضعیت را ببینید و کش ساخت قدیمی‌تر از یک هفته را پاک کنید:

به‌روزرسانی‌های امنیتی

اوبونتو به‌روزرسانی‌های امنیتی بسته‌های خودش، از جمله nginx، را با unattended-upgrades خودکار نصب می‌کند. Docker از مخزن خودش نصب شده و جزو این به‌روزرسانی خودکار نیست؛ آن را هر چند وقت یک بار با sudo apt update && sudo apt upgrade به‌روز کنید. بعد از به‌روزرسانی Docker، کانتینرهای فروشگاه با سیاست unless-stopped خودشان دوباره بالا می‌آیند.

پشتیبان‌گیری

فرانت‌اند داده‌ای ذخیره نمی‌کند و همهٔ داده‌ها در بک‌اند است. از سرور فروشگاه فقط این‌ها را نگه دارید: پوشهٔ /etc/firefly (فایل‌های تنظیمات و فونت‌های اختصاصی) و /etc/letsencrypt. کد در git است و ایمیج‌ها را می‌توان دوباره ساخت.

فونت اختصاصی

برای فونت اختصاصی دارای مجوز، فایل woff2 را در /etc/firefly/digital-font.woff2 بگذارید و در فایل تنظیمات THEME_FONT=custom را تنظیم کنید. اسکریپت این فایل را در هر استقرار به کانتینر وصل می‌کند و ساخت دوباره لازم نیست؛ فقط deploy را اجرا کنید.
